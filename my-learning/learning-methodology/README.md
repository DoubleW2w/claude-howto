# 快速学习方法论：二八法则 + 奥卡姆剃刀

> 二八法则定位"学什么"，奥卡姆剃刀决定"怎么学"。一个聚焦重点，一个砍掉废话。

---

## 核心理念

**二八法则（Pareto Principle）**：20% 的知识覆盖 80% 的使用场景。学习新领域时，你的任务不是"学多少"，而是找到那 20%，跳过剩余 80%。

**奥卡姆剃刀（Occam's Razor）**：如无必要，勿增实体。如果一句话能讲清楚，不要写一段；如果一个例子够用，不要给三个。组织信息时反复自问：删掉这个元素，读者还能理解吗？

两条原则分工明确：二八法则回答"学什么"——从海量信息中筛出高频核心；奥卡姆剃刀回答"怎么学"——用最小信息量传达最大理解。二八法则定位"学什么"，奥卡姆剃刀决定"怎么学"。一个聚焦重点，一个砍掉废话。

---

## 四步操作法

**第一步：定位信息源**

找到领域最权威的信息入口。优先级：官方文档 > 优质教程 > 博客文章。最多 2-3 个来源，避免信息过载。

**第二步：抓取骨骼**

只看结构，不读正文。提取：目录层级、核心概念列表（不超过 10 个）、关键 API/命令表、配置项清单。这一步的目标是建立领域地图，而非理解细节。

**第三步：提取核心**

用二八法则从骨骼中筛选 4-6 张核心概念卡。判断标准：
- "这个知识点，我日常工作中 80% 的场景会用到吗？"
- "没有它，我能开始工作吗？"

回答"否"的知识点放入"后续查阅"区。

**第四步：去噪成文**

用奥卡姆剃刀砍掉重复解释、评价性语言、冗余示例。保留所有技术细节。终止条件：如果资料已足够精炼，不再强行压缩。

**第四步半：可视化检查**

完成核心知识文档后，对照决策表判断是否需要生成 HTML 可视化：

| 条件 | 决策 | 说明 |
|------|------|------|
| 纯命令列表、纯配置值、纯文本 | ❌ 不生成 HTML | CLI 标志表、环境变量表、API 参数表 |
| 概念易混淆，需并列对比帮助理解 | ✅ 生成 HTML | 恢复 vs 总结、交互模式 vs 打印模式 |
| 场景描述 / 案例演示，**文字量大且不直观** | ✅ 生成 HTML | 文字阐述冗长时用动画替代 |
| 工作流 / 分支决策 / 状态轮转 | ✅ 生成 HTML | 权限模式选择路径、会话分叉流程 |
| 变化过程 / 数据流动 / 前后差异 | ✅ 生成 HTML | 管道串联、JSON 输出转换、重构前后 |
| **不确定属于哪类** | ⚠️ **必须询问用户** | 禁止自行猜测。问"这里需要生成可视化吗？" |

> **铁律**：判断不准时，问用户。不猜。不假设。"这里需要可视化吗？你觉得文字描述够清晰吗？"

这一子步骤强制要求：**每完成一个知识点的核心文档，必须记录可视化决策和理由**，防止遗漏。格式：

> **可视化决策**：[生成/不生成] HTML。理由：[一句话]。
> 如生成：调用 `frontend-design` 或 `huashu-design` 产出到 `assets/`。

详细的 Prompt 模板见 [prompt-templates.md](prompt-templates.md)。

## 完整演示：Checkpoints

以下用 Checkpoints 走一遍完整四步流程。

### 信息源

- `08-checkpoints/README.md`（教程原文）
- [官方 Checkpointing 文档](https://code.claude.com/docs/zh-CN/checkpointing)

### 骨骼

| 维度 | 内容 |
|------|------|
| 核心概念 (3) | Checkpoint 快照、Rewind 回退、Branch Point 分支点 |
| 访问方式 (3) | `Esc`+`Esc` 快捷键、`/rewind` 命令、`/checkpoint` 别名 |
| 回退选项 (6) | 从完整恢复到仅恢复代码/对话，再到总结压缩和取消 |
| 使用场景 (4) | 探索不同方案、安全重构、A/B 测试、错误恢复 |
| 局限性 (3) | Bash 命令变更不跟踪、外部变更不跟踪、不能替代版本控制 |
| 配置 (1) | `cleanupPeriodDays` 保留天数 |

### 提取核心

**保留（✅）：**

- 3 个核心概念：Checkpoint 快照、Rewind 回退、Summarize 压缩
- 6 种回退选项
- 4 种使用场景
- 3 种访问方式

**延后查阅（❌）：**

- 自动创建机制细节（每次用户提示自动创建、30 天清理策略）
- 清理配置 `cleanupPeriodDays`
- 故障排查（找不到 checkpoint、rewind 失败）
- 与 Git 集成的对比说明
- 上下文监控工具推荐

**保留率**：原文 335 行 → 核心内容约 80 行，保留率约 25%。

### 去噪成文

| 砍掉 | 保留 |
|------|------|
| 评价性语言（"非常有用""强烈推荐"） | 所有技术细节（选项类型、参数说明） |
| 重复的实战对话示例 | 最小可运行知识（核心概念卡 + 速查表） |
| 解释性冗余（同一概念多段落重复） | 一句话定义和关键对比（恢复 vs 总结） |

最终输出见 [Checkpoints 核心知识](../checkpoints/README.md)。

**可视化决策**：✅ 生成 4 个 HTML。理由：回退选项（6选1决策）、分支工作流（空间关系）、恢复vs总结（易混淆对比）、方法论流程（4步动画）。对应文件：`assets/rewind-options.html`、`workflow-patterns.html`、`restore-vs-summarize.html`、`methodology-flow.html`。

## 核心概念卡

### 二八法则操作卡

| 维度 | 内容 |
|------|------|
| 一句话 | 20% 的知识解决 80% 的问题 |
| 适用场景 | 新工具、新框架、新语言、新概念的学习 |
| 操作要诀 | 先看目录 → 标高频项 → 只学高频项 → 其余查阅 |
| 判断标准 | "这个知识点，我下一周会用到几次？" 少于 1 次 → 跳过 |
| 反例 | 学 Git 从内部实现开始而不是 `add`/`commit`/`push` |

### 奥卡姆剃刀操作卡

| 维度 | 内容 |
|------|------|
| 一句话 | 如无必要，勿增实体 |
| 适用场景 | 组织笔记、编写文档、设计解释 |
| 操作要诀 | 写完后自问"删掉这段，读者还能理解吗？" |
| 何时不用 | 安全警告、精确的法律/医学信息、API 参考文档 |
| 反例 | 为了"简洁"删掉 `rm -rf` 的危险提示 |

## 常见陷阱

| 陷阱 | 表现 | 解决方案 |
|------|------|----------|
| 过度精简 | 砍掉了理解核心概念所必需的上下文 | 核心概念至少保留一个可运行的完整示例 |
| 伪核心 | 把"目录"当"核心知识"，只会列标题 | 核心 ≠ 索引。每条核心必须包含具体用法 |
| 一成不变 | 对所有领域用同一套筛选标准 | 工具的 20% 是常用命令；框架的 20% 是核心概念+数据流 |
| 边际价值递减 | 对已经精炼的内容继续压缩 | 原始资料已精简时，不再强行砍内容。只做结构重排 |
| 跳过可视化检查 | 完成文档后直接结束，没有对照决策表 | 第四步半是强制步骤，完成文档后立即检查 |

## 适用边界

- ✅ **最适合**：工具类知识（CLI、IDE、DevOps）、框架类知识（React、Spring、Django）、概念类知识（设计模式、系统架构）
- ⚠️ **谨慎使用**：医学、法律等需要精确完整性的领域、安全相关的操作指南、考试备考
- 🎯 **经验法则**：如果"用错会出事"的知识，不适用此方法论。

## 可视化：何时生成 HTML

不是每个知识点都需要可视化。决策标准见上方的 [第四步半](#四步操作法) 决策表（v2）。

**怎么生成**：用 `frontend-design` 或 `huashu-design` 技能。选哪个取决于内容复杂度——简单对比用前者，复杂动画/交互用后者。风格统一一个主题。

> 这一节本身也是方法论的一部分：**不是所有知识都需要可视化**。奥卡姆剃刀同样适用——如果表格能讲清，就不做动画。
